# Languages: Czech, Slovak and English

Status: design, 2026-10-18, work for after the hackathon. The app
(`app/`) has the client side: the Fluent catalogs in
`i18n/<locale>/<area>.ftl`, loaded through `fluent-vue`
(`app/app/plugins/i18n.ts`, `app/app/lib/i18n.ts`), with Slovak and English
falling back to Czech; see [`FRONTEND.md`](FRONTEND.md), "As implemented".
The server phase and the meeting language are not built yet.

The app is Czech today. This design makes the interface available in
Czech, Slovak and English without touching the clinical evidence: what the
documents say stays in the language it was written in.

Terms used below:
- **UI language** (locale): the language of the interface a user picks: `cs`, `sk` or `en`.
- **Content language**: the language of the patient's documents. In practice Czech, possibly Slovak; never chosen by the user.
- **Meeting language**: the language spoken at the MDT, which speech-to-text and the AI summary need.
- **Catalog**: one JSON file per UI language holding every interface string under a key.

## How the frontend is built

The frontend is the Nuxt app in `app/` (Vue 3 in SPA mode, see
[`FRONTEND.md`](FRONTEND.md)), served by the API Worker at `/` with path
routes (`/patient/10/labs`, `/calendar/2026-10-19`). It loads its data from
the API. Besides the app, the Worker serves two small pages of its own: the
phone upload page `api/public/phone-upload.html` at `/u`, and the 404 page
written by `api/scripts/stage-assets.sh`. Both are Czech only.

The app registers `fluent-vue`, a Vue 3 plugin on `@fluent/bundle`.
`vue-i18n` and `@nuxtjs/i18n` are not used, because they use a different
message format.

## What changes language and what does not

| Kind of text | Examples | Rule |
|---|---|---|
| **Interface** | Navigation, tabs, buttons, headings, table headers, dialogs, toasts, tooltips, `aria-label`, placeholders, status names, alert kinds, error messages, empty states, PDF headings, FHIR section titles, the phone page, 404 pages | Translated through the catalogs |
| **Fixed clinical wording** (CLAUDE.md) | "neuvedeno v dostupné dokumentaci", "ověřit čtení", "zápor v dokumentu", "pozorování asistenta", "Rozhodnutí v diskusi nezaznělo." | Translated once, agreed by a clinician, stored in a glossary; never improvised per string |
| **Source evidence** | Quotes from documents (with their OCR errors), guideline statements (English or Czech as published), document titles as written, lab names, values, units and ranges, MKN-10 and lab codes, dates as written ("03/2024"), patient and staff names, transcript lines | Never translated |
| **Assistant text about the patient** | Brief, findings, alerts, drafted question, drafted tasks, AI recording summary, guideline "why it applies" | Stays in the content language (Czech) for now; see "Assistant text" |
| **Doctor-entered text** | Conclusions, notes, tasks, confirmed questions, edits, break-the-glass reasons | Stays as typed |
| **Approved records** | The report frozen at approval (`decisions.report_snapshot_json`), the PDF of an approved case | Stays in the language it was approved in: the snapshot stores its `locale` and a catalog version, and an approved PDF is rendered with that catalog, not the viewer's |
| **Organization data** | Department names, roles as the hospital names them | Stays as entered by the hospital |

### Assistant text

Every assistant sentence about the patient points to a verbatim quote in
the document's language. Three options for a Slovak or English interface:

1. **Keep it in the original language** (decided 2026-10-18; Czech
   today). It is what the extraction produced and checked against its
   quotes. Slovak readers read Czech without effort.
2. **Generate it per language at extraction time** (later, for English
   users; tracked in issue #12). This needs a pinned prompt per language, a re-check against
   the failure cases in CLAUDE.md per language, and alert IDs that do not
   hash the text (today `alerts.text_cs` is part of the alert ID).
3. **Translate it on the fly** (rejected). A second model pass can drop a
   negation or change a value, and nothing would check it.

For an English interface, option 1 means English chrome around Czech
clinical text. That is honest, but only usable by readers of Czech. Option
2 is the path if the app ever serves English-only users.

## Mechanism: Fluent on the browser's `Intl`

**Decision (2026-10-18): Fluent**, Mozilla's localization system: messages
in `.ftl` files, read by the `@fluent/bundle` runtime (about 4 KB min +
gzip). Formatting of dates, numbers and lists uses the built-in `Intl`
APIs. Measured in the browser and in the local Workers runtime:
- `Intl.PluralRules` knows the Czech and Slovak categories (one, few, many, other) and the English ones (one, other).
- `DateTimeFormat`, `NumberFormat`, `ListFormat` and `RelativeTimeFormat` format all three languages correctly.
- `Collator` sorts "ch" after "h" in Czech and Slovak.

**Why Fluent:**
- **Plurals and variants per language.** A Czech message can have four plural forms while the English one has two, and a translator can add a variant (a grammatical case, a gender) in one language without any code change.
- **Terms.** A term is a shared definition referenced by many messages. The fixed clinical wording is defined once per language as a term, so it cannot drift between screens.
- **Shared with citry,** which uses Fluent too, so a citry screen can read the same catalogs.
- **Translation tools** (Mozilla's Pontoon, Weblate, Crowdin) read `.ftl`.

Options considered:

| Option | Size (min + gzip) | Verdict |
|---|---|---|
| Fluent (`@fluent/bundle`) | about 4 KB | Chosen |
| Own `t()` + `Intl`, JSON catalogs | about 0.3 KB | Smallest; plural objects and every grammar variant written by hand |
| intl-messageformat (FormatJS, ICU MF1) | 9.6 KB | Widest tool support; weaker for Slavic variants |
| i18next | 13.8 KB (26 KB with ICU) | Heaviest; its own plural key convention |
| vue-i18n (`@nuxtjs/i18n`) | part of Nuxt | Its own plural syntax (`a \| b \| c`), custom rules needed for Czech and Slovak, and `@ { } \| $` are special characters |

Costs of Fluent, accepted:
- **Fewer people and coding agents know it** than JSON or ICU catalogs.
- **The core library releases rarely** (last 0.19.1, April 2025); the format is stable.
- **One default must be turned off:** `useIsolating: false`. Otherwise every placeholder is wrapped in invisible direction marks, which break copy-paste and text comparisons in tests.

No library solves Czech and Slovak declension of a noun placed inside
another sentence. The rule that does: write each sentence whole per
language, and prefer "label: value" layouts. Fluent terms with case
variants are available where a sentence really needs one.

### Catalogs

`i18n/cs.ftl`, `i18n/sk.ftl`, `i18n/en.ftl` (split per area once they
grow, for example `i18n/cs/patient.ftl`). Czech is the source of truth.
Example:

```ftl
nav-patients = Databáze pacientů
labs-values = { $n ->
    [one] { $n } hodnota
    [few] { $n } hodnoty
    [many] { $n } hodnoty
   *[other] { $n } hodnot
}
upload-done-by = Nahrál(a) { $name }, { $time }

# Fixed clinical wording (CLAUDE.md): defined once as terms.
-gap-not-stated = neuvedeno v dostupné dokumentaci
gap-not-stated = { -gap-not-stated }
```

- **Message IDs** are semantic and namespaced in kebab case, never the Czech text: `nav-patients`, `patient-tab-labs`, `common-save`. The fixed clinical wording lives in terms named `-gap-*` and `-trust-*`.
- **Numbers.** `{ $n }` is formatted with `Intl.NumberFormat`, so it gets the decimal comma in Czech and Slovak. `many` is only for fractions in Czech and Slovak (1,5 dne), but every plural message for those two still carries it.
- **Default variant.** Fluent requires a default variant (`*[other]`), so a missing category never shows an empty string.

### The runtime

In the app, `app/app/lib/i18n.ts` builds the bundles on `@fluent/bundle`
and `fluent-vue` hands them to the components. The rules:
- **Bundles and fallback.** One `FluentBundle` per language, with `useIsolating: false`. A message missing in Slovak or English falls back to Czech, logs a warning in development, and fails the CI check (see "Tooling").
- **`t(id, args)`** formats the message and collects Fluent's errors instead of throwing.
- **Escaping.** Fluent does not escape. The wrapper escapes every argument before formatting, because the result goes into `innerHTML` or an attribute.
- **Markup inside a message.** Some sentences need markup: bold parts, line breaks, a link. Messages may use only tags from a short allow-list (`<b>`, `<br>`, `<a>` with an `href` argument), written in the catalog; everything else is escaped. In Vue, `fluent-vue`'s `<i18n>` component fills named slots instead, so no raw HTML is needed there.
- **IDs are static.** Write `status-scheduled`, not `` `status-${s}` ``, so the unused-message check works. Where an ID must be built (status codes), list the possible IDs next to the code.
- **`fmt.*`.** `fmt.date`, `fmt.time`, `fmt.dateTime`, `fmt.number`, `fmt.list`, `fmt.relative` and `fmt.compare` wrap `Intl`, with instances cached per locale.
  - A partial date ("03/2024") is formatted as month and year. It never becomes a full `Date`, per CLAUDE.md.
- **Number input** accepts both `,` and `.` as the decimal mark in every language, as the lab input already does.
- **Loading.**
  - The app registers `fluent-vue` (3.8, a Vue 3 plugin on `@fluent/bundle`) in a Nuxt plugin (`app/app/plugins/i18n.ts`). There is no official Nuxt module; registering it is a few lines. Czech is in the first load; Slovak and English load only when chosen.
  - The Worker would import the `.ftl` files as text imports (server phase).

### Gender forms

The Czech "nahrál(a)" style is kept, and Slovak gets "nahral(a)". English
has no such form. The user directory has no gender. Fluent could select
"nahrál" or "nahrála" from a `$gender` argument, but adding gender to the
directory only to inflect verbs is not worth the data.

## Choosing the language and passing it on

### On the client

1. **Order of choice:**
   1. `?lang=sk` in the URL (handy for demo links);
   2. the stored choice;
   3. the deployment's default language: Czech today, Slovak for a Slovak hospital.

   The browser's language does not decide. A jury laptop set to English would otherwise open the demo in English, which is not the demo the presenter knows.
2. **Storage:** a `lang` cookie (so the Worker can read it) and `localStorage` (wrapped in try/catch). Once logins exist, also a `users.locale` column.
3. **Switcher:** a small "CS / SK / EN" select in the header next to the user select. It is plain, with no banner and no notice; the default stays Czech, so the demo looks as it does today.
4. **Switching without a reload:**
   1. `setLocale`;
   2. set `document.documentElement.lang`, which screen readers and hyphenation use;
   3. Vue re-renders what reads the messages.
   
   Text being typed survives only where its form keeps its value in a store (the MDT question, the conclusion and the notes do); other dialogs are closed on switch.
5. **Fallback:** both sk and en fall back to cs (the source) for any key not yet translated. The CI check keeps that from happening in a release.

### On the server

- **Errors.** Every error gets a unique `message_key` and `params`, next to today's `code` (which stays for logic) and `message_cs`, which stays as the fallback. The client shows `t(message_key, params)`. Today one code can carry several messages (`not_doctor` has four), so the code alone is not enough.
- **Access log.** It stores `action` plus `params_json` and renders the sentence in the client, in the reader's language.
  - Today the server writes a finished Czech sentence (`what_cs`) at about 86 places in `api/src`, and the client sends 32 more. The client even maps sentences back to codes with regular expressions (`VIEW_EVENTS`), which translation would break.
  - An audit record must not change after it is written. So each new row also keeps the Czech sentence rendered at write time, and `params_json` is never edited. A catalog change then cannot alter what an old entry said.
  - Old rows have only `what_cs`. An administrator reading the log in Slovak or English sees those rows in Czech: a mixed-language log, accepted for history written before the change.
- **Labels sent as text.** `state_cs`, `readability_cs`, `STATUS_CS` and the status-history "how" text become codes. The client translates them.
- **Text the server renders itself** (later e-mail): the locale comes from `users.locale`, then the `lang` cookie, then the deployment default. A notification e-mail is rendered in the recipient's locale, not the sender's.
- **404 pages** are static files written by `deploy.sh` and `stage-assets.sh`. They become one small page with the message in all three languages.
- **The page reader (PageKit, Python)** returns readability and redaction reasons as Czech text (`reasons_cs`), and its tests assert that text. These become codes with parameters, translated in the client like the server's labels.
- **Coded values.** `patients.sex` stores `'muž'`/`'žena'`; it becomes a code (`male`/`female`).

### Meeting language

- **It belongs to the recording, not to the viewer.** A Slovak doctor may use the Slovak interface while the MDT speaks Czech.
- **Recording start:** it records `language` on the recording row. The default is the seminar's language, a setting per department, which is Czech today. `STT_LANGUAGE` moves from global configuration to that row, and both ElevenLabs calls use it. ElevenLabs lists Czech and Slovak in its top accuracy tier.
- **Summary:** it uses a prompt per meeting language (`summarize-cs`, `summarize-sk`). The prompt version is already part of the summary cache key, so caching stays correct.
  - A Slovak summary is assistant text in Slovak. Its prompt, its fixed sentence for "no decision was made" and its output need the same clinician sign-off and failure-case check as any extraction prompt.
- **Stored summary:** it stores its language. Every viewer sees the same draft.

### PDF and FHIR

- **Built in the browser,** so they follow the UI language at export time.
- **FHIR** translates only section titles and our own labels.
  - `Composition.language` follows the content language (Czech narrative stays labelled Czech), not the UI language.
  - `Coding.display` stays as the code system gives it.
- **An approved case's PDF** uses the frozen snapshot, in the language it was approved in.

## What has to be refactored first

The number of strings is the easy part. These places used Czech text as
identifiers or stored data in mock v3 (the single-file page the app
replaced); check each in the app, `packages/domain` and the Worker, and
change what remains before translation can work:

1. **Access log:**
   - `logAccess(pid, "otevřel(a) případ")` stores sentences (32 calls);
   - `VIEW_EVENTS` parses them back with regular expressions;
   - they become `logAccess(pid, "case.open", params)`.
2. **Display strings used as keys:**
   - the default user is found by `"Klinická onkologie"`;
   - doctors are detected by "MUDr." in a name;
   - the admin is found by display name;
   - column filters store display text (`STATUS[...][0]`, document types);
   
   All become IDs or codes. (Three more checks compare extracted `label_cs` values to Czech strings; those are content, not interface, and stay as long as the content is Czech.)
3. **Formatted dates stored as data.** `S.access[].when`, `pr.when` and the mails' `when` are already `cs-CZ` strings, and `fmtWhen` turns API timestamps into Czech strings when loading the status history, decisions, suggestions and edits. Every one becomes an ISO timestamp, formatted when shown.
4. **Split words and assembled sentences:**
   - `"Syntetický pacient: z" … "pracované"` splits one word across a condition;
   - several sentences are built from parts with ternaries.
   
   They become whole messages.
5. **The plural helper.** `plural(n, one, few, many)` hard-codes the Czech rule (11 uses), and 8 more full sentences hand-code it. All move to catalog plurals.
6. **Text in CSS:** `content: "Zatím žádný přepis."` moves to markup.
7. **Hand-written formats:**
   - `fmtDate`, `dayLabel`, `ageText` (" let");
   - the manual decimal comma in `fmtSize` and on the phone page.
   
   They move to `fmt.*`.

## What stays Czech-only on purpose (content features)

These read the documents or the doctor's text, not the interface. A Slovak
interface does not change them, but Slovak *documents* would need work:

- **Due dates in drafted tasks.** The rules in `packages/domain/src/suggest.ts` (`SUGG_RULES`, `NEG_RE`, `TIMING_RE`, Czech month names) parse Czech conclusions. A Slovak conclusion would partly fail, including its negations, which matters.
- **OCR** runs with Tesseract `ces`. Slovak documents need `slk` and recalibrated readability thresholds.
- **Diagnosis codes.** The FHIR code system for MKN-10 is the Czech one (`uzis.cz`). A Slovak export needs the Slovak code system.
- **Insurers.** Slovak insurer codes differ (VšZP 25, Dôvera 24, Union 27). `patients.insurer` is free text, so nothing breaks; the "Nový pacient" select lists Czech codes only.

Each becomes its own task only if Slovak hospitals send Slovak documents.

## Tooling and checks

- **`scripts/i18n_check.py`** (Python, like the build; it parses `.ftl` with Mozilla's `fluent.syntax` package) fails CI when:
  - a key used in code is missing from a catalog, or a catalog key is unused;
  - placeholders differ between languages;
  - a plural message lacks a category its language needs;
  - Czech text (diacritics) appears in code outside the catalogs, with an allow-list for data and tests.
- **Content marked with its language.** Every place that shows content (quotes, names, values, codes, dates as written, assistant text) is wrapped in an element with `lang="cs"` (or the content's language).
  - Screen readers then pronounce Czech quotes correctly inside an English interface.
  - The pseudo-locale test can skip them.
  - The app's static `<html>` tag has `lang="cs"` (`app/nuxt.config.ts`), and `app/app/plugins/i18n.ts` keeps it in step with the chosen language.
- **Pseudo-locale `xx`.** It is the Czech catalog run through `@fluent/bundle`'s `transform` option, never translated: every string is accented, about 35 % longer and bracketed (`[Ďàťàβàžé ƥàčíéɳťů~~~]`). Opening the app in `xx` shows any hard-coded string at a glance, and long text that breaks the layout. It is development only.
- **Tests.**
  - The existing Vitest and Playwright tests assert Czech text and use Czech department names as selectors. They keep running in `cs`.
  - New tests render each screen in `sk`, `en` and `xx`. In `xx` they fail on any visible text outside a `lang`-marked element that is not wrapped in brackets.
  - The S02 intake and phone-upload flows get one run in `sk` and `en`.
- **Catalogs hold no patient names or examples,** synthetic or not, so a catalog can go to a translation model or tool safely.
- **Translation workflow:**
  - Czech is the source.
  - Slovak and English drafts are made by an LLM, with the terms (the fixed clinical wording) given as the glossary. Only interface strings go to the model, never patient data.
  - Medical terms and the fixed clinical wording need review by a native-speaking clinician, because Slovak medical terms differ from Czech in real ways. The team names one owner per language for the glossary and its sign-off.
  - Review happens in pull requests. A translation management tool (Weblate, Tolgee, Crowdin) is not needed until outside translators or more than about five languages.

## Regulatory note

If the app becomes a medical device, EU MDR Art. 10(11) requires the label
and instructions for use in each member state's language. Czech law (Act
375/2022 Sb., §39) requires Czech instructions. Whether a software
interface counts is handled differently by member states. This is not
needed for the prototype; it matters for a product and is checked then
with a regulatory advisor.

## Decisions (2026-10-18)

- **Assistant text stays in the original language** (Czech today) for
  every UI language. Generating it per language at extraction time is
  issue #12.
- **Fixed clinical wording in Slovak and English:** the proposals are
  adopted: "neuvedené v dostupnej dokumentácii" and "not stated in the
  available documentation"; "overiť čítanie" and "verify reading". A
  clinician signs them off before release; then they go into CLAUDE.md
  next to the Czech wording.
- **Meeting language:** a setting per department (Czech today), stored on
  each recording when it starts.
- **Default UI language per deployment:** Czech today; a Slovak hospital
  defaults to `sk`.
- **A recording does not switch language mid-meeting.** Its language is
  fixed when it starts; another language means stopping and starting a new
  recording.
